# Sidekick C++ Code Generation Guidelines

## Overview

`internal/sidekick/cpp` is the C++ code generation engine in Librarian. It converts service specifications (`api.API`) into idiomatic C++ client libraries matching the architecture of `google-cloud-cpp`.

Generation follows the Sidekick model:
1. **Annotation / Codec:** The C++ codec enriches `api.API` with C++-specific annotations (`serviceAnnotations`, `methodAnnotations`, `fieldAnnotations`, etc.).
2. **Template Rendering:** The annotated model is passed to Mustache templates (`internal/sidekick/cpp/templates/*.mustache`) to render C++ source files (`*.h`, `*.cc`).
3. **Formatting:** Emitted source files are formatted in-place using `clang-format`.

---

## 1. Annotation Model Design

### 1.1. Package-Private Annotations
- All annotation structs must be **private to the package**:
  - `serviceAnnotations`
  - `methodAnnotations`
  - `fieldAnnotations`
  - `commentAnnotations`
  - `optionsAnnotations`
  - `signatureAnnotations`
- Helper and nested structs must also remain unexported. Do not export annotation types unless strictly required and documented.

### 1.2. Strongly-Typed Fields Only (No Dynamic Maps or "Vars")
- **Never use dynamic maps or untyped dictionaries** (`map[string]any`, `map[string]string`) for annotations or template data contexts.
- All annotation fields must be static, known, and strongly typed.
- This guarantees compile-time type safety and clear template contracts.

### 1.3. Methods for Derived Values
- If an annotation value can be derived in 2–3 lines from other model fields, **implement it as a method on the annotation struct** rather than storing an eager field.
- *Examples*:
  - Method on `serviceAnnotations`: `IncludeGuard() string`, `HeaderFileName() string`, `Namespace() string`.
  - Method on `methodAnnotations`: `HasMethodSignatureOverloads() bool`, `IsStreaming() bool`.
  - Method on `fieldAnnotations`: `CppType() string`, `IsRepeated() bool`.

---

## 2. Codec Configuration & Architecture

### 2.1. Swift-Style Config Structs Over Maps
- Model codec options using strongly-typed Go configuration structs rather than unstructured option maps (following `internal/sidekick/swift` rather than older `internal/sidekick/rust` patterns).

### 2.2. Decomposed Structure & 1:1 Tests
- Decompose concerns into focused source files (`annotate_service.go`, `annotate_method.go`, `annotate_field.go`, `annotate_comments.go`, `names.go`, etc.).
- Pair every source file with a dedicated `_test.go` file (`annotate_service_test.go`, etc.).

---

## 3. Equivalence Standard & Formatting

### 3.1. 100% Byte-for-Byte Parity
- Emitted code must produce zero difference (`diff -u`) against reference golden and production files.
- Retain the exact banner comment:
  ```cpp
  // Generated by the Codegen C++ plugin.
  // If you make any local changes, they will be lost.
  ```
- Retain exact copyright headers with configurable initial year.

### 3.2. Direct `clang-format` Invocation
- Emitted code is formatted directly with `clang-format -i`.
- System `clang-format` on `$PATH` is used by default, with optional override in `librarian.yaml` under `tools: clang_format:`.

---

## 4. Testing Conventions

### 4.1. Test Assertions via `extractBlock()`
- Prefer `extractBlock(t, content, startStr, endStr)` over whole-file diffs or loose `strings.Contains()` in unit tests.
- Isolates discrete sections of generated code (specific method overloads, class definitions, include guards) for robust, focused assertions.

### 4.2. Hermetic Unit Tests vs Integration Tests
- Unit tests must remain hermetic and fast, running with `go test -short ./...` using fixtures in `internal/sidekick/cpp/testdata/`.
- Tests requiring remote network I/O or repository downloads must use `//go:build integration`.
- **Never use hardcoded `$HOME` paths** in test code or configuration. Use dynamic SHA resolution from build files.

### 4.3. Test Data Builders
- Always use `api.NewTest*()` constructors (`api.NewTestAPI`, `api.NewTestService`, `api.NewTestMethod`, etc.) from `internal/sidekick/api/test.go`. Never instantiate raw `api.*` structs directly.

---

## 5. Review & Verification Protocol

### 5.1. Post-Phase Consistency Review
- After completing any phase or milestone, execute the `review-pr` skill from `.agents/skills/review-pr/SKILL.md` using the consistency prompt:
  > "Review the change for consistency. Make sure the comments for all files touched by the change match the code. Make sure the names use consistent names."
- Run standard verification:
  ```bash
  gofmt -s -w .
  go tool goimports -w .
  go tool golangci-lint run
  go test -short ./...
  ```

### 5.2. Post-Phase Subagent Verification
- After each phase, invoke a subagent to compare the working tree against `migration_plan.md`.
- If the subagent detects any architectural deviations or missing requirements, **stop immediately and ask the user for guidance**.

### 5.3. Brief Commit Messages
- Commit messages during development must be brief (e.g. `docs(cpp): add migration plan and coding guidelines`).
